# 中古オフィスチェア価格監視 設計

日付: 2026-11-11
状態: 承認済み

## 目的

オカムラ「シルフィー」またはイトーキ「アクト」の肘付き（可動）を、中古で 30,000 円以内で買う。
条件に合う出品が新しく出たとき、または値下げで条件に入ったときに LINE へ通知し、取り逃がしを防ぐ。

成功の基準: 条件に合う出品が出てから概ね 30 分以内に LINE に届き、同じ出品について同じ通知が重複しない。

## スコープ

対象サイト:

- オフィスバスターズ
- ビックリユース
- オフィスレスキュー119
- メルカリ

やらないこと:

- iOS アプリ、Web 画面（設定はコードと Secrets で持つ）
- 送料込みでの判定（表示価格で判定する）
- 可動肘か固定肘かの画像判定（文字で判断できない分は通知の写真を見て人が判断する）
- 購入の自動化

## 構成

公開 GitHub リポジトリ（`subscription-tracker` とは別）で、GitHub Actions から Python のスクリプトを定期実行する。

```
.github/workflows/watch.yml   15分おきの cron と手動実行（workflow_dispatch）。state.json に差分があればコミットして push
src/chair_watch/
  models.py      Listing（site, item_id, title, price_yen: int, url, image_url, description: str | None）
  sources/       サイトごとに1ファイル。検索して list[Listing] を返す
    officebusters.py
    bicuse.py
    rescue119.py
    mercari.py
  filters.py     条件の判定（通信しない純粋関数）
  diff.py        前回 state と比べた通知対象の判定（通信しない純粋関数）
  notify_line.py LINE Messaging API への push
  main.py        取得 → 判定 → 差分 → 通知 → state 保存
state.json      監視中の出品の記録
tests/          filters と diff の単体テスト、保存した HTML/JSON を使った各 source の解析テスト
```

依存ライブラリ: `httpx`、`selectolax` または `beautifulsoup4`（HTML 解析）、`playwright`（メルカリ用。必要な場合だけ使う）、テストは `pytest`。

## 検索

スパイク（2026-11-11、GitHub Actions 上で実施）の結果、次の方法で読む。価格はすべて税込の表示価格。

| サイト | 読むもの | 検索語・対象 |
|---|---|---|
| オフィスバスターズ（officebusters.com） | シリーズ別一覧ページの 1 ページ目（新しい順 60 件） | `/series/okamura/sylphy/`、`/series/okamura/Sylphymesh/`、`/series/itoki/act-chair*/` の 4 つ |
| ビックリユース（bic-reyouth.shop） | 検索画面が裏で呼ぶ `kanri.bic-reyouth.com/api/shop/product/search` の JSON | シルフィ / アクト。在庫 0（SOLD OUT）は除く。割引期間中は割引後の価格 |
| オフィスレスキュー119（119happy.com） | 詳細検索結果の HTML（検索語は Shift_JIS） | シルフィー / イトーキ アクト |
| メルカリ | Playwright で検索画面を開き、画面が受け取る `entities:search` の JSON | オカムラ シルフィー / イトーキ アクト。販売中、3 万円以下、新しい順 |

サイトごとの事情:

- オフィスバスターズの検索ページ（`/kensaku/`）は robots.txt で全クローラに禁止されているため、許可されているシリーズ一覧を使う。1 ページ目だけ読むので、61 件目以降の古い出品が値下げされても拾えない
- オフィスバスターズの一覧の商品名は「肘付」までしか分からず、固定肘も通知されていた。3 万円以下の肘付きだけ詳細ページを読み、キャッチコピー・タグ・商品説明（下の「おすすめ商品」欄は除く）を判定に加える。どこか 1 か所でも「固定肘」があれば除外する（キャッチコピーやタグが「固定肘」なのに商品説明が「可動肘」という食い違いもあったため）（2026-11-12 追加）
- 詳細ページから読んだ内容は `detail_cache.json` に保存し、同じ出品の詳細ページは 1 回しか読まない。検索結果から消えた出品の分は消す
- オフィスレスキュー119 の一覧には肘の有無が書かれていない。3 万円以下のシルフィー / アクトだけ、詳細ページの「タイプ」欄（肘付 / 肘無）を読んで判定に使う
- メルカリは API（`/v2/`）が robots.txt で禁止されていて、直接呼ぶには署名も必要なため、許可されている検索画面を開く。検索結果に説明文はなく、ブランド名を説明文の代わりに使う
- メルカリは件数を抑えるためにサイト側で 3 万円以下に絞る。そのため、3 万円を超えていた出品が値下げされて入ってきた場合は「値下げ」ではなく「新着」として通知される

## 判定（filters.py）

すべてタイトルと説明文（取得できた場合）に対して、大文字小文字や全角半角をそろえてから判定する。

1. 製品: 次のどちらかを満たす
   - シルフィー系: 「シルフィー」「シルフィ」「sylphy」のどれかと、「オカムラ」「okamura」のどちらかを含む。または、チェアのカテゴリから取得した出品である
   - アクト系: 「アクト」「act」のどちらかと、「イトーキ」「itoki」のどちらかを含む
2. 肘あり: 「肘」「ひじ」「アーム」のどれかを含む
3. 除外: 「肘なし」「肘無」「アームレス」（「アームレスト」は除く）「アームなし」「固定肘」「肘固定」のどれかを含むものは外す
4. 部品の除外: タイトルに「シルフィー用」「アクトチェア用」「パーツ」「部品」「肘置き」「スポンジ」「左右セット」「パッドのみ」などがあれば外す
5. 肘の種類が書かれていない肘付きは除外しない（可動か固定かは写真で判断する）
6. 肘について何も書かれていない出品は、メルカリだけ対象にする。カードに「肘：記載なし（写真で確認）」と表示する。スパイクで、メルカリのタイトルの多くに肘の記載がなかったため（2026-11-12 に利用者の希望で追加）。ほかのサイトでは対象外

1〜3 を満たした出品を「監視対象」とし、価格に関係なく state に記録する。
通知するのは、監視対象のうち `price_yen <= 30000` のものに限る。

## 差分（diff.py）

state のキーは `"{site}:{item_id}"`、値は最後に見た価格。

- 新着: キーが state になく、価格が 30,000 円以下
- 値下げ: キーが state にあり、今回の価格が前回より安く、今回の価格が 30,000 円以下（前回が 3 万円を超えていた場合も、3 万円以下のままさらに下がった場合も含む）
- 値上げ、または価格が同じ: 通知せず、state だけ更新する
- 検索結果から消えた出品（売り切れなど）: state から外す。ただし、そのサイトの取得が成功した回だけ外す

## エラー処理

- 1 サイトの取得や解析に失敗しても、ほかのサイトは処理を続ける。失敗したサイトの state はそのまま残す
- 0 件の結果は「解析失敗の疑い」として扱う。前回 1 件以上あったのに今回 0 件なら、失敗と同じく state を残す
- 同じサイトが 3 回続けて失敗したら、LINE に「〇〇の取得に失敗しています」と 1 回だけ送る。成功したら回数を 0 に戻す。連続失敗の回数は state.json に持つ
- 初回実行（state.json がない、またはそのサイトの記録がない）では、今ある 3 万円以下の出品をすべて新着として通知する（2026-11-12 に利用者の希望で変更）
- LINE の設定がなく送れなかった回は state.json を保存しない。送れなかった通知を送ったことにしないため
- LINE への送信に失敗した場合は state を更新せず、ワークフローを失敗させる。次の実行で同じ通知を送り直す

## 通知（notify_line.py）

- LINE Messaging API の push メッセージで、自分のユーザー ID に送る
- Flex Message のカルーセルで送り、1 件をカード 1 枚にする（商品写真、タイトル、価格、新着か値下げか（値下げなら旧価格 → 新価格）、サイト名、商品ページを開くボタン）
- カルーセル 1 通に最大 12 件まで載せる。超える場合は 2 通に分ける
- `altText`（プッシュ通知で見える文）は「新着2件・値下げ1件」のような要約にする
- 無料プランの上限（月 200 通）に対して、通知は 1 回の実行で最大でも数通に収まる想定

## 設定と秘密情報

GitHub Secrets:

- `LINE_CHANNEL_ACCESS_TOKEN`
- `LINE_USER_ID`

価格の上限（30000）、検索語、除外語はコード内の定数で持つ。

## 定期実行

- cron は `*/15 * * * *`。GitHub の混雑で数分〜十数分遅れることがある
- 公開リポジトリなので Actions の実行時間に上限はない
- 公開リポジトリで 60 日間活動がないと scheduled workflow は止まる。state.json のコミットが続く限りは問題ない想定だが、止まっていないかは月に一度確認する
- ワークフローに `concurrency` を設定して、前回の実行と重ならないようにする

## リスクとスパイク

スパイクで、GitHub Actions から 4 サイトとも取得できることを確かめた（メルカリも Playwright で検索結果を受け取れた）。

- 各サイトの利用規約で自動アクセスがどこまで認められているかは、利用者が自分で確認する
- 取得する間隔とアクセス数は控えめにする（15 分に 1 回、1 回の実行でサイトごとに数リクエスト程度）
- 画面の作りが変わると読めなくなる。連続失敗の通知で気づけるようにしている

開発用のクラウド環境からは各サイトに直接つながらないため、サイトの中身は GitHub Actions 上で取得して確かめた。

## テスト

- filters: 製品名の表記ゆれ、肘あり・肘なし・固定肘、日産「シルフィ」の部品の除外
- diff: 新着、値下げ（3 万円超から 3 万円以下、3 万円以下のままさらに値下げ）、値上げ、消えた出品、取得失敗時に state を残すこと、初回は今ある出品をすべて新着として通知すること
- sources: スパイクで保存した実際の検索結果の HTML/JSON を fixture にして、解析結果を確かめる
- notify_line: 送信する JSON の組み立てだけをテストし、実際の送信は手動実行で確認する
